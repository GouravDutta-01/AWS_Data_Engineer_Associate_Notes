# Amazon S3(Simple Storage Service)

## 1. Overview
Amazon S3 (Simple Storage Service) is an object storage service designed for:
- High durability (11 nines)
- Infinite scalability
- Low-cost storage
- Data lakes, backups, analytics, ingestion pipelines

---

## 2. Buckets
- Bucket = top-level container for objects
- Bucket names are **globally unique**
- Buckets are **regional**

### Bucket Naming Rules
- 3–63 characters
- Only lowercase letters, numbers, hyphens
- Must not look like an IP address
- Cannot start with “xn--”
- Cannot end with “-s3alias”

---

## 3. Objects
- Stored in buckets
- Each object has:
  - **Key** (full path name)
  - **Value** (data)
  - **Metadata**
  - **Version ID** (if versioning enabled)
  - **ACL** (optional)

### Object Keys
S3 has **no directories** — folders are simulated using "/" prefixes.

Example:
s3://my-bucket/logs/2024/01/file.json


---

## 4. Versioning
- Disabled by default
- Once enabled → **cannot be turned off**, only suspended
- Protects against accidental overwrites/deletes
- Delete = “delete marker” (non-destructive)

---

## 5. Encryption
S3 supports encryption **in transit** and **at rest**.

### At-Rest Encryption Options
1. **SSE-S3** – AWS managed keys (AES-256)
2. **SSE-KMS** – KMS CMK, most secure, auditable
3. **SSE-C** – customer-provided keys
4. **Client-side encryption** – encrypt before upload

**Notes:**
- SSE-KMS adds KMS cost and request quota overhead.

---

## 6. Storage Classes
| Storage Class | Use Case | Key Notes |
|---------------|----------|-----------|
| **S3 Standard** | Hot data | Fastest, multi-AZ |
| **S3 Standard-IA** | Infrequent access | Retrieval cost applies |
| **S3 One Zone-IA** | Re-creatable data | Single AZ |
| **S3 Glacier Instant Retrieval** | Archive + fast access | 1–2ms |
| **S3 Glacier Flexible Retrieval** | Backup | Minutes–hours |
| **S3 Glacier Deep Archive** | Long-term | Cheapest |
| **S3 Intelligent-Tiering** | Auto cost optimization | Monitoring fee |

### Automatic Transitions
Define via **Lifecycle Policies**.

---
### S3 Storage Class Transition 

- **Intelligent-Tiering** is the ONLY class that automatically transitions objects (no lifecycle rule needed).
- Intelligent-Tiering auto-tiering applies only to objects > 128 KB.
- All other storage classes require an S3 Lifecycle rule for transitioning.
- Minimum storage durations before transitioning or deletion:
    - IA classes (Standard-IA, One Zone-IA):
        - Objects must remain **30 days in IA** before they can be transitioned or deleted without early-deletion fees.
        - There is **no minimum age required in Standard** before moving into IA.
    - Glacier classes:
        - Must remain in their respective Glacier tier for **90 days (Instant/Flexible)** or **180 days (Deep Archive)**.
        - Early deletion fees apply if moved or deleted earlier.
    - Glacier objects cannot auto-transition back to Standard/IA; you must Restore to access them.
- Lifecycle transitions are applied only by prefix or object tags, never bucket-wide.
- Cross-Region Replication does NOT copy lifecycle rules (must recreate manually).
---

## 7. Lifecycle Management
Used to automatically transition or expire objects.

### Examples
- Move to IA after 30 days
- Transition to Glacier Deep Archive after 180 days
- Delete incomplete multipart uploads after 7 days

---

## 8. Replication
Two types:
### **1. CRR (Cross-Region Replication)**
- Replicate to **another region**
- For compliance, disaster recovery

### **2. SRR (Same-Region Replication)**
- Replicate within **same region**
- For log aggregation / data lakes

### Notes
- Versioning must be enabled **on both buckets**
- Replication is **not retroactive** unless explicitly enabled
- Delete markers can be optionally replicated

## 9. S3 Request Types
Important for cost and exam questions:

- PUT, GET, DELETE
- LIST (expensive at scale)
- HEAD
- POST Multipart Upload
- COPY (server-side)

## 10. Performance Optimization

### Prefix-Based Optimization (Old)
Used to matter; no longer required — S3 automatically scales.

### Performance Features
- **Multipart Upload**
  - Required for >100MB, recommended for >5GB
- **S3 Byte-Range Fetches**
  - Speed up downloads, parallelization

---

## 11. Consistency Model
S3 provides:
- **Strong read-after-write consistency** for:
  - PUT
  - DELETE
  - LIST
- Applies across all regions

---

## 12. Access Control

### IAM Policies
- Define **who** in your AWS account can access S3.
- Attached to IAM **users, roles, and groups**.
- Best for **most access scenarios** (recommended by AWS).
- Evaluated at the **identity level**.

### Bucket Policies
- JSON policies attached directly to the **bucket**.
- Used mainly for **cross-account access**, public access (e.g., static website), or enforcing security conditions.
- Support conditional rules (VPC endpoints, IP ranges, encryption required).
- Evaluated at the **resource level**.

### ACLs (Access Control Lists)
- **Legacy**, low-level access control for specific AWS accounts.
- Support **object-level** permissions (read/write).
- Only needed when:
  - You host a **static website** and must allow public read.
  - You handle **cross-account object uploads** and need ownership control.
- In modern S3, ACLs are often disabled with **Bucket Owner Enforced** mode.

---

## 13. S3 Block Public Access
Always tested.

Prevents public access at:
- Account level
- Bucket level

Recommended to **enable always** unless hosting a static site.

---

## 14. S3 Security Best Practices
- Use IAM roles (never long-term credentials)
- Enable Bucket Versioning
- Use MFA Delete for extra protection
- Use SSE-KMS encryption for sensitive data
- Use VPC Endpoints to avoid public internet

---

## 15. S3 Event Notifications
Trigger on operations such as:
- PUT
- POST
- DELETE
- Multipart upload completion

Targets:
- SNS
- SQS
- Lambda

**Note:** Cannot send events to two destinations for same prefix+suffix combination.

## 16. S3 Select & Glacier Select
Query object data using SQL.

### S3 Select
- Supports CSV, JSON, Parquet
- Retrieve specific columns instead of full object

### Glacier Select
- Works with archived data with some delays

---

## 17. S3 Access Logs & Storage Lens
### Server Access Logs
- Store detailed request logs into another bucket
- Useful for security audits

### S3 Storage Lens
- Dashboard for:
  - Object counts
  - Storage usage
  - Access patterns

---

## 18. S3 Data Protection
- **Cross-Region Replication (CRR)** for DR
- **Versioning** for rollback
- **MFA Delete** for admin protection
- **Object Lock (WORM)**:
  - Prevents object deletion for a retention period
  - Useful for compliance (GRC, SEC)

Modes:
- Governance
- Compliance

---

## 19. S3 for Data Engineering Use Cases
- Raw zone → S3 Standard
- Staging/Processing zone → Standard or Intelligent-Tiering
- Long-term archive → Glacier Deep Archive
- Logs → One Zone-IA or Standard-IA
- Data ingestion (Kinesis Firehose → S3)

---

## 20. Important Notes
- **Replication requires versioning**  
  S3 replication (CRR or SRR) only works when versioning is enabled on both the source and destination buckets.

- **SSE-KMS has extra cost and throttling limits**  
  Using SSE-KMS adds charges for KMS key usage and can hit KMS request quotas under heavy load (common in ingestion pipelines).

- **S3 is not a file system**  
  You cannot append to an existing object; you must rewrite or use multipart upload for large files.

- **S3 Select helps reduce cost for large objects**  
  It allows retrieving only specific rows/columns instead of downloading the full object, saving bandwidth and query cost.

- **Intelligent-Tiering charges a monitoring fee**  
  Small objects (<128 KB) are not eligible for automatic tiering, and there is a monthly monitoring cost per object.

- **Storage class transitions have minimum age requirements**  
  Many storage classes (like IA or Glacier tiers) require that an object stay in Standard for at least 30 days before transitioning.

- **Cross-account bucket access does not automatically mean cross-account role access**  
    - Allowing Account B to access a bucket in Account A requires a bucket policy.
    - Allowing Account B to assume a role in Account A requires a trust policy.
    - These are two different mechanisms and do not grant each other automatically.
